# Pulumi (TypeScript) + Pulumi Cloudflare provider for bluelytics_v2

Research date: 2026-11-22. No Cloudflare credentials were available: nothing in this file was applied against a real account. Everything marked RUN was reproduced locally with a dummy token on a `file://` Pulumi backend.

## 0. Bottom line, evidence legend, versions

### 0.1 Bottom line

Use architecture **C**: Pulumi owns the long-lived account and zone resources (D1 database, KV namespace, R2 bucket + custom domain + lifecycle + CORS, DNS records that Cloudflare does not create itself, the zone entry point Rulesets). Wrangler owns everything that is part of a Worker deployment (code, static assets, bindings, custom domains/routes, cron triggers, Workers Cache settings, secrets) and applies D1 migrations in the deploy job. Resource IDs flow one way: Pulumi stack outputs -> committed `wrangler.jsonc` values, with a CI check that fails on drift.

Do not deploy the Astro Worker through `WorkersScript`/`WorkerVersion`. It can be made to preview (section 2), but the provider ignores `.assetsignore`, does not interpret `_headers`/`_redirects`, needs the hashed chunk list generated by hand, and the split resources are still labelled beta upstream.

## 1. Worker code resources: `WorkersScript` vs `Worker` + `WorkerVersion` + `WorkersDeployment`

### 1.1 Which one is recommended

- Upstream docs for `cloudflare_workers_script` (v5.29.0, https://github.com/cloudflare/terraform-provider-cloudflare/blob/v5.29.0/docs/resources/workers_script.md): "For more direct control over Workers resources, we recommend the beta `cloudflare_worker`, `cloudflare_worker_version`, and `cloudflare_workers_deployment` resources." (SRC). So the split trio is recommended by Cloudflare but still called **beta**.
- Pulumi's own template "Cloudflare Static Website" (https://www.pulumi.com/dev/templates/static-website/cloudflare/, Last-Modified 2026-11-21) uses `Worker` + `WorkerVersion` (assets) + `WorkersDeployment` (DOC).
- Cloudflare IaC guide (https://developers.cloudflare.com/workers/platform/infrastructure-as-code/, 2026-11-19): "Notice how you do not have to manage all of these resources in Terraform. For example, you could use just the `cloudflare_worker` resource and seamlessly use Wrangler or your own deployment tools for Versions or Deployments." and "None of the examples below do Workers Bundling"; bundle first with `wrangler deploy --dry-run --outdir build` (DOC).
- Recommendation for this project: neither for code (section 11). If code must go through Pulumi: `WorkersScript` for a single-file API bundle; the split trio only if version/deployment separation (gradual rollouts) is wanted.

### 1.2 API endpoints behind the resources (DOC, IaC guide 2026-11-19 and API reference)

| Resource | Endpoint |
| --- | --- |
| `WorkersScript` | `PUT https://api.cloudflare.com/client/v4/accounts/{account_id}/workers/scripts/{script_name}` (multipart: JSON `metadata` part + one part per module; ES modules use content type `application/javascript+module`) |
| `Worker` | `POST /accounts/{account_id}/workers/workers`; `DELETE /accounts/{account_id}/workers/workers/{worker_id}` (only these two methods appear in the guide's examples) |
| `WorkerVersion` | `POST /accounts/{account_id}/workers/workers/{worker_id}/versions` |
| `WorkersDeployment` | `POST /accounts/{account_id}/workers/scripts/{script_name}/deployments` |

Accepted token permission for script upload: `Workers Scripts Write` (API reference https://developers.cloudflare.com/api/resources/workers/subresources/scripts/methods/update/, fetched 2026-11-22).

### 1.3 `WorkersScript` inputs (SCHEMA)

Required: `accountId`, `scriptName`. Main optional inputs:

- Code: `content` (inline) or `contentFile` + `contentSha256`; `mainModule` (ES module syntax; name of the entry part) or `bodyPart` (service-worker syntax); `contentType`; `files: { [partName]: { contentFile | contentBase64, contentType } }` for additional modules (added upstream in 5.25.0: "files: Multipart WASM modules and binary files included in the Worker upload", CHANGELOG, SRC).
- Runtime: `compatibilityDate`, `compatibilityFlags`, `placement { mode }`, `limits { cpuMs, subrequests }`, `observability { enabled, headSamplingRate, logs { enabled, invocationLogs } }`, `logpush`, `tailConsumers`, `cacheOptions { enabled, crossVersionCache }` (the Workers Cache switch, section 6.5).
- Bindings: `bindings[]`, `keepBindings[]` (binding *types* to keep from the previous upload), `bindingsInherit` (`"strict"`), `migrations {...}` (Durable Objects).
- Assets: `assets { directory, config { htmlHandling, notFoundHandling, runWorkerFirst, headers, redirects, basePath }, jwt }`, `keepAssets`.
- Outputs: `etag`, `hasAssets`, `handlers`, `startupTimeMs`.

Replace-on-change: `scriptName`, `accountId` (SRC `schema.go`; the Pulumi schema carries no replace flags).

Use `browser`.

### 1.5 Validated example: single-module API Worker (RUN: type-checks, previews)

```ts
import * as crypto from "node:crypto";
import * as fs from "node:fs";
const sha256File = (p: string) => crypto.createHash("sha256").update(fs.readFileSync(p)).digest("hex");

const api = new cloudflare.WorkersScript("api", {
  accountId,
  scriptName: "bluelytics-api",
  mainModule: "index.js",                       // required for ES module Workers
  contentFile: "build/api/index.js",            // relative to the Pulumi project dir
  contentSha256: sha256File("build/api/index.js"), // mandatory together with contentFile
  compatibilityDate: "2026-11-01",
  compatibilityFlags: ["nodejs_compat"],
  bindings: [
    { type: "d1", name: "DB", id: db.id },
    { type: "kv_namespace", name: "CACHE", namespaceId: kv.id },
    { type: "r2_bucket", name: "MEDIA", bucketName: media.name },
    { type: "plain_text", name: "ENVIRONMENT", text: "production" },
    { type: "secret_text", name: "X_API_SECRET", text: cfg.requireSecret("xApiSecret") },
  ],
  observability: { enabled: true, headSamplingRate: 1, logs: { enabled: true, invocationLogs: true } },
  cacheOptions: { enabled: true, crossVersionCache: true },
});
```

### 1.6 Validated example: split resources (RUN: type-checks, previews)

```ts
const worker = new cloudflare.Worker("web", {
  accountId, name: "bluelytics-web",
  observability: { enabled: true },
  subdomain: { enabled: false, previewsEnabled: false },
});
const version = new cloudflare.WorkerVersion("web-version", {
  accountId, workerId: worker.id,
  mainModule: "entry.mjs",
  compatibilityDate: "2026-11-01", compatibilityFlags: ["nodejs_compat"],
  modules: [
    ...serverModules.map((f) => ({ name: f, contentType: "application/javascript+module", contentFile: `${serverDir}/${f}` })),
    { name: "_headers", contentType: "text/plain", contentFile: `${clientDir}/_headers` },
  ],
  assets: { directory: clientDir, config: { htmlHandling: "auto-trailing-slash", notFoundHandling: "404-page", runWorkerFirst: false } },
  bindings: [{ type: "assets", name: "ASSETS" }, { type: "d1", name: "DB", id: db.id }],
});
new cloudflare.WorkersDeployment("web-deployment", {
  accountId, scriptName: worker.name, strategy: "percentage",
  versions: [{ versionId: version.id, percentage: 100 }],
  annotations: { workersMessage: "deployed by pulumi" },
});
```

`WorkerVersion` is immutable: any change produces a new version (replacement); `WorkersDeployment.strategy` only accepts `"percentage"` (SCHEMA). `WorkerVersion` also has a `deploy` boolean ("If true, a deployment will be created that sends 100% of traffic to the new version", SCHEMA).

### 1.7 Gotchas found by running the provider (RUN unless tagged)

1. Files are read at **preview** time. `contentFile`, `files[*].contentFile`, `modules[*].contentFile` and `assets.directory` must exist before `pulumi preview`, so the build has to run first. Relative paths resolve against the Pulumi project directory.
2. `contentFile` without `contentSha256`: `Attribute "content_sha256" must be specified when "content_file" is specified`. Wrong hash: `SHA-256 Hash Mismatch`. Missing file: `Hash Calculation Error`.
3. `files[*].contentSha256` is listed as an input in the Pulumi schema but setting it fails with `Invalid Configuration for Read-Only Attribute`. Only pass `contentFile` + `contentType` there.
4. A `d1` binding needs an ES module Worker: set `mainModule` (pulumi-cloudflare issue #1309, open, https://github.com/pulumi/pulumi-cloudflare/issues/1309).
5. Upgrading a stack that already holds a `WorkersScript` with `assets.config.runWorkerFirst` can fail in `UpgradeResourceState` (pulumi-cloudflare issue #1497, open, reported for 6.10.0 -> 6.13.0). Not reproduced here.
6. `secret_text.text` is never returned by the API; the provider restores it from state on read (SRC `workers_script/resource.go`). The value therefore lives in Pulumi state (encrypted, because the schema marks it secret).
7. Secrets set outside Pulumi (for example `wrangler secret put`) are not adopted into state (upstream 5.14.0, PR #6504 "handle workers_script resource drift when worker has unmanaged secret", SRC). INFERENCE: to stop a Pulumi upload from dropping them, pass `keepBindings: ["secret_text"]`; the API describes `keep_bindings` as "List of binding types to keep from previous_upload" (DOC, API reference above). Apply-time behaviour UNVERIFIED.
8. Durable Object bindings to a class in the same script fail on the first apply; the IaC guide prescribes a two-step apply (DOC). Not relevant unless Durable Objects are introduced.
9. Churn: upstream 5.19 through 5.29 each contain `workers_script` / `worker_version` drift or state-migration fixes, and 5.29.0 lists breaking changes (CHANGELOG, SRC, https://github.com/cloudflare/terraform-provider-cloudflare/blob/v5.29.0/CHANGELOG.md). Pin the provider version exactly.

## 2. Static assets (`assets.directory`)

- Introduced in `terraform-provider-cloudflare` 5.11.0 (2025-10-02, PR #6160 "support for handling Workers Assets uploads", for both `cloudflare_workers_script` and `cloudflare_worker_version`) = `@pulumi/cloudflare` v6.10.0 (2025-10-03). Announced at https://developers.cloudflare.com/changelog/post/2025-10-09-assets-terraform/ (2025-10-09). 5.7.0 fixed `headers`/`redirects`; 5.13.0 extended `run_worker_first` (SRC CHANGELOG).
- What the provider does (SRC `workers_script/assets.go`): walks every file under `directory`, builds a manifest, then performs the three-step direct upload: `POST /accounts/{account_id}/workers/scripts/{script_name}/assets-upload-session` -> `POST /accounts/{account_id}/workers/assets/upload?base64=true` -> script upload with the completion JWT (DOC https://developers.cloudflare.com/workers/static-assets/direct-upload/, 2026-11-12). The same page says: "Directly uploading assets via APIs is an advanced approach which, unless you are building a programmatic integration, most users will not need. Instead, we encourage users to deploy your Worker with Wrangler".
- Config fields (SCHEMA): `WorkersScript.assets.config` has `htmlHandling` (`auto-trailing-slash` | `force-trailing-slash` | `drop-trailing-slash` | `none`), `notFoundHandling` (`none` | `404-page` | `single-page-application`), `runWorkerFirst` (boolean or list of path patterns; type `Any`), `headers` (contents of a `_headers` file as a string), `redirects` (contents of `_redirects`), `basePath`. `WorkerVersion.assets.config` has **no** `headers`/`redirects`; upstream docs: "`_headers` and `_redirects` files should be included as modules named `_headers` and `_redirects` with content type `text/plain`" (SRC `docs/resources/worker_version.md`).
- Validated (RUN): `WorkersScript` with `assets.directory`, `runWorkerFirst: ["/api/*", "!/_astro/*"]`, `headers: fs.readFileSync(".../_headers", "utf8")`, plus `files` for extra modules; `WorkerVersion` with `runWorkerFirst: false`. A missing directory fails preview with `Error reading asset files - lstat ...`.
- Limits (DOC https://developers.cloudflare.com/workers/platform/limits/, 2026-11-19): 20,000 asset files per Worker version on Free (100,000 Paid), 25 MiB per file. Billing (DOC https://developers.cloudflare.com/workers/static-assets/billing-and-limitations/, 2026-11-12): "Requests to static assets are free and unlimited."

Known issues when the directory is an Astro build (RUN build of Astro 7.4.13 + `@astrojs/cloudflare` 14.4.9):

1. `dist/client/` contains `_headers` (the adapter injects `/_astro/*  Cache-Control: public, max-age=31536000, immutable`) and `.assetsignore` (listing `wrangler.json` and `.dev.vars`). The provider has no `.assetsignore` handling and does not special-case `_headers`/`_redirects` (SRC). INFERENCE: they would be uploaded as ordinary public files and the header rules would not apply unless also passed through `assets.config.headers` (WorkersScript) or as a module (WorkerVersion).
2. `dist/server/` is a multi-module, unbundled Worker: `entry.mjs` plus `chunks/*.mjs` with content-hashed names (for example `chunks/_astro_assets_CAD0uaDa.mjs`) and `virtual_astro_middleware.mjs`. The `files`/`modules` list must be generated by listing the directory on every build. This works at preview (RUN) but each build changes the resource inputs.
3. The adapter also writes `dist/server/wrangler.json` (generated config: `main: "entry.mjs"`, `no_bundle: true`, `rules: [{type: "ESModule", globs: ["**/*.js","**/*.mjs"]}]`, `assets: {binding: "ASSETS", directory: "../client"}`, `upload_source_maps: true`) and `.wrangler/deploy/config.json` redirecting wrangler to it. With Pulumi all of that has to be mirrored by hand, including source maps.
4. Asset content type is derived with Go `mime.TypeByExtension` (SRC). INFERENCE: unknown extensions may get an empty content type. UNVERIFIED at apply.

## 3. D1

```ts
const db = new cloudflare.D1Database("db", {
  accountId,
  name: "bluelytics",
  primaryLocationHint: "enam",            // wnam | enam | weur | eeur | apac | oc
  readReplication: { mode: "disabled" },  // auto | disabled
}, { protect: true });
```

- Inputs (SCHEMA): `accountId`*, `name`*, `primaryLocationHint`, `readReplication { mode* }`, `jurisdiction` (`eu` | `fedramp` | `us`), `fields` (list of response fields to request; not needed).
- Replace-on-change (SRC `d1_database/schema.go`): `name`, `primaryLocationHint`, `jurisdiction`, `accountId`. Upstream docs: "When a D1 Database is replaced all the data is lost." Always set `protect: true` and never rename.
- Verifier RUN (2026-11-22, state created by `pulumi up` against a local mock of the D1 endpoints, then `pulumi preview --diff`): changing `name`, changing **or removing** `primaryLocationHint`, adding `jurisdiction`, and changing `accountId` each plan `+-1 to replace`; changing `readReplication.mode` plans an in-place update. With `protect: true` the preview fails with `unable to replace resource ... as it is currently marked for protection`, so the flag does block the data loss. The create request body was `{"name","primary_location_hint","read_replication":{"mode"}}` on `POST /accounts/{account_id}/d1/database`.
- **Adoption hazard (verifier, mock RUN + API reference).** The D1 `GET` response model has `created_at, file_size, jurisdiction, name, num_tables, read_replication, uuid, version` and no `primary_location_hint` (https://developers.cloudflare.com/api/resources/d1/subresources/database/methods/get/, fetched 2026-11-22). Importing an existing database (`import: "<account_id>/<database_id>"`) while the program sets `primaryLocationHint` therefore plans `= 1 to import` **and** `+-1 to replace` in the same operation (reproduced against a mock that omits the hint, as the reference does). Without `protect` that would delete the database. When adopting a database that was not created by this program, omit `primaryLocationHint` (import alone then plans cleanly) and keep `protect: true`. A database created by the program itself keeps the hint in state and shows no diff on refresh (RUN against the mock). Behaviour of the real API not exercised.
- Import ID: `<account_id>/<database_id>` (SCHEMA). Discover IDs with `GET /accounts/{account_id}/d1/database` (permission `D1 Read`).
- Token permission: `D1 Read`, `D1 Write` (SCHEMA resource description).

Migrations: the provider has **no** migration resource (the only D1 resource in the schema is `D1Database`). Options:

| Option | How | Verdict |
| --- | --- | --- |
| wrangler in CI | `wrangler d1 migrations apply <DATABASE> --remote` | Recommended |
| `@pulumi/command` | `local.Command` running the same command, `triggers: [hashDir("migrations"), db.id]` | Works at preview (RUN) but hides SQL changes inside `pulumi up` |
| REST | `POST https://api.cloudflare.com/client/v4/accounts/{account_id}/d1/database/{database_id}/query` with `{"sql": "...", "params": [...]}` or `{"batch": [...]}`; also `/raw`, `/import`, `/export` (API reference fetched 2026-11-22; permission `D1 Write`) | Only for ad-hoc tooling |

Wrangler migration facts (DOC https://developers.cloudflare.com/d1/reference/migrations/, 2026-06-08, and https://developers.cloudflare.com/d1/wrangler-commands/, 2026-04-21):

- Migrations are `.sql` files in `migrations/`, applied in filename order; applied ones are recorded in the `d1_migrations` table. `migrations_dir`, `migrations_table`, `migrations_pattern` are configurable per `d1_databases` entry.
- "When running the apply command in a CI/CD environment or another non-interactive command line, the confirmation step will be skipped, but the backup will still be captured."
- `<DATABASE>` is "The name or binding of the DB" and is resolved through the wrangler config, so the config must contain the `d1_databases` entry with the real `database_id`.
- RUN observation: Astro's generated config rewrites `migrations_dir` relative to `dist/server/` (`"../../migrations"`). Keep migrations in the API package and run the command from there.

## 4. KV

```ts
const kv = new cloudflare.WorkersKvNamespace("cache", { accountId, title: "bluelytics-cache" });
new cloudflare.WorkersKv("kv-schema-version", { accountId, namespaceId: kv.id, keyName: "meta:schema_version", value: "1" });
```

- `WorkersKvNamespace` inputs (SCHEMA): `accountId`*, `title`*, `jurisdiction`, `mode`. Import ID `<account_id>/<namespace_id>`. Replace-on-change: `jurisdiction`, `mode` (SRC).
- `WorkersKv` inputs: `accountId`*, `namespaceId`*, `keyName`*, `value`*, `metadata`, `expiration`, `expirationTtl`. Import ID `<account_id>/<namespace_id>/<key_name>`. Only use it for static seed values; runtime data belongs to the Worker.
- Permissions: `Workers KV Storage Read/Write` (SCHEMA). List namespaces: `GET /accounts/{account_id}/storage/kv/namespaces`.
- Astro note (RUN + DOC https://docs.astro.build/en/guides/integrations-guide/cloudflare/): the adapter adds a `SESSION` KV binding without an ID and relies on wrangler automatic provisioning, unless `session: false` is set in `astro.config.mjs` (RUN: with `session: false` the generated config has no `SESSION` binding). Set `session: false` if sessions are not used, otherwise an unmanaged KV namespace appears on first deploy.

### 6.5 Caching Worker responses: Workers Cache, not zone Cache Rules

This changes what the Rulesets are for.

- https://developers.cloudflare.com/workers/cache/ (2026-10-30): "**No zone configuration for caching applies to Workers Caching.** Cache Rules, Cache Response Rules, Page Rules, cache level settings, the zone's default cached-file-extensions list, and every other zone-level cache control have no effect on a Worker's cache."
- https://developers.cloudflare.com/workers/reference/how-the-cache-works/ (2026-10-29): "Cloudflare Workers run before the cache".
- Enable per Worker: wrangler `"cache": { "enabled": true, "cross_version_cache": true }` (`cache` needs wrangler >= 4.69.0; `cross_version_cache` needs >= 4.107.0; DOC https://developers.cloudflare.com/workers/cache/configuration/, 2026-10-30). Provider equivalent: `cacheOptions { enabled, crossVersionCache }` on `WorkersScript`/`WorkerVersion` (SCHEMA, RUN).
- Behaviour is driven by the response's `Cache-Control`. Only `GET` and `HEAD` are cached (DOC https://developers.cloudflare.com/workers/cache/limitations/, 2026-11-18). Without `cross_version_cache` every deploy starts with a cold cache.
- Billing (same doc family): "Workers Cache has no separate pricing. When you enable Workers Cache, all requests to your Worker are billed at the standard Workers request rate ... whether the response comes from cache or from your Worker. ... CPU time is only billed when your Worker runs". Consequence: cache hits still count toward the Free plan's 100,000 requests/day, and enabling it on a Worker with static assets makes otherwise-free asset requests billable. Verifier: this is no longer an inference. The same page states "When caching is enabled, every request to your Worker is charged at the standard Workers request rate, including requests that are normally free: static asset requests and worker-to-worker invocations", and the pricing page (https://developers.cloudflare.com/workers/platform/pricing/, 2026-11-18, footnote 4 and "Example 5: Worker with caching") says "Cache hits count as requests but do not consume CPU time." So do **not** enable `cache` on the Astro Worker that serves static assets; enable it only on the API Worker.
- The Cache API (`caches.default`) remains available inside a Worker (DOC https://developers.cloudflare.com/workers/reference/how-the-cache-works/, 2026-10-29: "Caching responses generated by the Worker itself through `cache.put()`"). INFERENCE: the Worker still has to run to read that cache, so it does not reduce the number of Worker requests.
- The zone cache (and therefore the Cache Rules ruleset) still applies to the R2 custom domain.

## 8. Rulesets (cache, redirect, URL rewrite, response headers)

### 8.1 One entry point ruleset per phase

- "Each phase has at most one entry point ruleset at the account level and at the zone level." The entry point's `kind` is `zone` at zone level, `root` at account level (DOC https://developers.cloudflare.com/ruleset-engine/about/rulesets/, 2026-04-16).
- "Cloudflare automatically creates the entry point ruleset when you add a rule to it, if it does not exist." (DOC https://developers.cloudflare.com/ruleset-engine/rulesets-api/create/, 2026-04-16). So any rule ever created in the dashboard for a phase means the entry point already exists.
- Consequences:
  1. Exactly one `cloudflare.Ruleset` per `(zoneId, phase)`; all rules of that phase go in its `rules` array, in evaluation order.
  2. If the zone already has rules in a phase, **import** the existing entry point instead of creating a new one. Look it up with `GET https://api.cloudflare.com/client/v4/zones/{zone_id}/rulesets/phases/{phase}/entrypoint` and import as `zones/<zone_id>/<ruleset_id>`. "The API returns a `404 Not Found` HTTP status code ... When a ruleset cannot be found." (DOC https://developers.cloudflare.com/ruleset-engine/rulesets-api/view/, 2026-04-16), so a 404 means the phase is still empty and a plain create is correct.
  3. The resource is authoritative for the whole list: rules added in the dashboard afterwards are removed on the next `pulumi up`. Destroying the resource deletes the entry point and with it every rule of the phase.
     Verifier evidence (2026-11-22). DOC: "The update operations described in this page (`PUT` requests) replace the entire list of rules in the ruleset. If you omit existing rules from the request body, those rules will be removed." (https://developers.cloudflare.com/ruleset-engine/rulesets-api/update/, 2026-04-16); "Terraform assumes that it has complete control over account and zone rulesets. If you already have rulesets configured in your account or zone, do one of the following: Import existing rulesets ... [or] Start from scratch by deleting existing rulesets" and "Each zone supports one entry point ruleset per phase. Define all your ... rules for a given zone within a single `cloudflare_ruleset` resource" (https://developers.cloudflare.com/terraform/additional-configurations/rate-limiting-rules/, 2026-04-29). RUN against a local mock API that logs requests: create sends `POST /zones/{zone_id}/rulesets` (not a `PUT` to the phase entry point, so it cannot merge into an existing entry point); update sends `PUT /zones/{zone_id}/rulesets/{ruleset_id}` with the program's complete `rules` array; removing the resource sends `DELETE /zones/{zone_id}/rulesets/{ruleset_id}`.
     **Import does not preserve existing rules.** With the `import` resource option and a program whose rules differ from the existing entry point, one `pulumi up` plans `= 1 to import` plus `~ 1 to update` and overwrites the rule list in the same run (mock RUN: a pre-seeded "dashboard" rule was gone after the `up`). Before adopting, copy every existing rule into the program and check that `pulumi preview --diff` shows the import with no `~ rules` update.
  4. Exact API error when a second entry point is created for the same phase: UNVERIFIED (no credentials).
- Replace-on-change: `name`, `kind`, `phase`, `zoneId`/`accountId` (SRC).
- Always set `ref` on each rule: "To keep existing rule IDs when making changes to a ruleset through Terraform, add a `ref` field to each rule. ... Once you set the `ref` field of a rule, changing the `ref` field value will make Terraform create a new rule." (DOC https://developers.cloudflare.com/terraform/troubleshooting/rule-id-changes/, 2026-04-21).

```ts
    },
  }],

new cloudflare.Ruleset("redirect-rules", {
  zoneId, name: "default", kind: "zone", phase: "http_request_dynamic_redirect",
  rules: [{

    actionParameters: { fromValue: {

new cloudflare.Ruleset("transform-rules", {
```

### 8.4 Plan-time dry-run (SRC `internal/services/ruleset/resource.go` + RUN)

- During preview the provider calls the Rulesets API with `?dry_run=true` (`POST /zones/{zone_id}/rulesets?dry_run=true` on create). It skips the call when the config is not fully known or when state equals plan.
- On **create**, a 400 from the dry-run is downgraded to a warning; on **update** it is a hard preview error. Non-400 failures (401, 429) are warnings.
- With the network fully blocked the provider panics: `Bridged provider panic ... nil pointer dereference` at `ruleset.(*RulesetResource).validateWithDryRun.func1 (resource.go:488)`. Previewing Rulesets therefore needs network access; a valid token is needed for the dry-run to mean anything. Verifier (re-run 2026-11-22 in a separate project, network namespace with only loopback up): same panic, same frame (`resource.go:488`, bridge v3.143.0), exit 1; the other resource types previewed with exit 0. Reading the source at v5.29.0, line 488 is `if res.Body != nil` in a deferred function and `res` is filled by `option.WithResponseBodyInto(&res)`; INFERENCE: the panic is triggered by any transport-level failure of the dry-run call (DNS, connect, TLS, timeout), not only by a fully offline machine, and it is reached from the plan step of `pulumi up` as well. An HTTP error status (401, 429, 400) does not panic. Treat a panic in CI as retryable and do not run Ruleset previews in a sandbox without egress to `api.cloudflare.com`.
- Many Rulesets in one preview with a bad token produced `429 Too Many Requests` (code 10429) warnings from the API (RUN).
- Other open provider issues touching Ruleset: pulumi-cloudflare #782, #710, #630 (not reproduced).

## 9. Secrets

- There is **no** per-secret Worker resource in 6.24.0. The schema's secret-related resources are `SecretsStore`, `SecretsStoreSecret` (account-level Secrets Store) and the `secret_text` binding inside `WorkersScript`/`WorkerVersion` (SCHEMA).
- Wrangler (DOC https://developers.cloudflare.com/workers/wrangler/commands/workers/, 2026-10-26, and https://developers.cloudflare.com/workers/configuration/secrets/, 2026-11-21):
  - `wrangler deploy --secrets-file <path>`: "Path to a file containing secrets to upload alongside the deployment. Accepts JSON or `.env` format ... Existing secrets not included in the file are preserved from the previous version."
  - "Secrets are never deleted by a deployment". SRC: wrangler's upload always adds `keep_bindings: ["secret_text", "secret_key"]`.
  - `wrangler secret put <KEY>` "creates a new version of the Worker and deploys it immediately"; `wrangler secret bulk [FILE]` uploads many at once.
  - `"secrets": { "required": ["NAME", ...] }` in the wrangler config: "`wrangler deploy` and `wrangler versions upload` will fail with a clear error if any required secrets are not configured". Accepted by wrangler 4.166.0 (RUN dry-run).
  - First deploy (verifier, SRC `wrangler@4.166.0` `addRequiredSecretsInheritBindings`): when the Worker does not exist yet and a required secret is not in the upload, `wrangler deploy` throws "The following required secrets have not been set: ... This Worker does not exist yet, so secrets cannot be set in advance with `<secret put command>`. To deploy a new Worker with secrets, supply them via a secrets file" (the command name is interpolated). So the very first deploy of a Worker with `secrets.required` must pass `--secrets-file` (the workflow in section 13 does). `keepSecrets: true` is set in `deployWorker` and `uploadWorkerVersion`, which is what produces `keep_bindings: ["secret_text", "secret_key"]`.
- Secrets Store (DOC https://developers.cloudflare.com/secrets-store/, 2026-08-14: "Available in open beta"; Workers integration https://developers.cloudflare.com/secrets-store/integrations/workers/, 2026-10-12): wrangler binding `secrets_store_secrets: [{ binding, store_id, secret_name }]`; API `POST /accounts/{account_id}/secrets_store/stores/{store_id}/secrets`; provider permission `Secrets Store Read/Write`. Not needed for this project; it is beta and the value is read with `await env.<BINDING>.get()` instead of a plain string.

Recommended flow for architecture C: keep social-API credentials as GitHub Actions environment secrets, write them to a JSON file in the deploy job and pass `--secrets-file`; declare the names in `secrets.required`. Alternative with a single source of truth: Pulumi config secrets exported as a secret stack output and read with `pulumi stack output --show-secrets --json workerSecrets` (program text in 11.3 previews correctly, RUN; the round trip into wrangler was not executed).

Design note (INFERENCE): secret bindings are fixed at deploy time, so OAuth tokens that the Worker must refresh at runtime cannot live only in a secret binding. They need a writable store (D1 or KV), seeded once.

## 10. Provider configuration and API tokens

- Provider inputs (SCHEMA): `apiToken` (env `CLOUDFLARE_API_TOKEN`), `apiKey` + `email` (legacy), `apiUserServiceKey`, `baseUrl`, `userAgentOperatorSuffix`. There is **no** provider-level `accountId`: every account-scoped resource takes `accountId`, every zone-scoped one takes `zoneId`.
- Simplest setup: no explicit provider, token from the environment. Or `pulumi config set --secret cloudflare:apiToken <token>`.
- The provider validates the token format before any request: `^[0-9A-Za-z\-_]{40,80}$` (SRC `internal/provider.go`; RUN: the string `dummy` is rejected at preview, forty zeros are accepted).
- Token formats (DOC https://developers.cloudflare.com/fundamentals/api/get-started/token-formats/, 2026-10-23): new user tokens are `cfut_` + 40 characters + checksum, account-owned tokens `cfat_...`; older 40-character tokens keep working. Verify with `GET https://api.cloudflare.com/client/v4/user/tokens/verify` and `Authorization: Bearer <token>`.
- Account-owned tokens (DOC https://developers.cloudflare.com/fundamentals/api/get-started/account-owned-tokens/, 2026-10-23) are meant for CI and are marked compatible with Workers, Workers KV, D1, R2, DNS, Rulesets, Cache; **Page Rules are not supported** with them.

| Account | Workers R2 Storage: Edit | `R2Bucket`, `R2CustomDomain`, lifecycle, CORS |

| Preview of code/binding changes | Yes, but the build must run before every `pulumi preview` | None: the command is opaque to Pulumi | `wrangler deploy --dry-run` in PRs |
| Secrets | In Pulumi state (`secret_text`) | Token passed through Pulumi | `--secrets-file` / CI secrets |
| D1 migrations | Needs `local.Command` anyway | `local.Command` | Deploy job step |
| Coupling | Every app deploy is a `pulumi up` holding the state lock | Same | Infra changes rarely; app deploys never touch state |
| Provider maturity | Split resources beta; frequent drift fixes (1.7 item 9) | n/a | Only stable, simple resources in Pulumi |
| Rollback | New version through `pulumi up` | wrangler | `wrangler rollback` / dashboard, independent of infra |

A is acceptable only for a single-file API Worker. B gives the drawbacks of both. C matches Cloudflare's own guidance ("We recommend treating your Wrangler configuration file as the source of truth for your Worker configuration", wrangler configuration doc, 2026-11-12) while still putting the stateful and zone-level pieces under Pulumi.

CORRECTED by the verifier: the earlier advice here that the Astro `_headers` file is "the safer place for site headers" only holds for prerendered pages and other static assets. Cloudflare: "Custom headers defined in the `_headers` file are not applied to responses generated by your Worker code, even if the request URL matches a rule defined in `_headers`. If you use a server-side rendered (SSR) framework, have configured `assets.run_worker_first`, or otherwise use a Worker script, you will likely need to attach any custom headers you wish to apply directly within that Worker script." (https://developers.cloudflare.com/workers/static-assets/headers/, 2026-11-12; the Astro adapter guide says the same, https://docs.astro.build/en/guides/integrations-guide/cloudflare/). `_headers` is also limited to 100 rules and 2,000 characters per line. So: `_headers` for prerendered HTML and assets, Astro middleware (or the API Worker's own `Response` headers) for on-demand routes; a response-header Ruleset is an optional third layer whose effect on Worker responses must be checked with `curl -I` after the first deploy.

Facts that shape the ID flow (RUN):

- `astro build` reads the user `wrangler.jsonc` and bakes it into `dist/server/wrangler.json`; `wrangler deploy` then prints "Using redirected Wrangler configuration". IDs must be in `wrangler.jsonc` **before** the build.
  - Verifier RUN (2026-11-22, fresh project, astro 7.4.13 + `@astrojs/cloudflare` 14.4.9 + wrangler 4.166.0): confirmed. Editing `wrangler.jsonc` after the build has no effect; `wrangler deploy --dry-run` still showed the KV ID that was present at build time.
  - CORRECTED nuance: this does **not** mean IDs cannot be injected at deploy time. `dist/server/wrangler.json` is plain JSON and wrangler reads it as is; changing `kv_namespaces[0].id` in that file after the build was honoured by `wrangler deploy --dry-run` (RUN). So a CI step between `astro build` and `wrangler deploy` can write the Pulumi stack outputs into `dist/server/wrangler.json` (and into `apps/api/wrangler.jsonc`, which has no build-time bake) instead of committing IDs. Committing the IDs plus the drift check below remains the simpler choice; the generated file's shape is an adapter implementation detail and may change between versions.
- Wrangler automatic provisioning makes a missing identifier **fail open** (verifier; DOC https://developers.cloudflare.com/workers/wrangler/configuration/#automatic-provisioning, 2026-11-12: "add bindings to your configuration file *without* adding resource IDs, or in the case of R2, a bucket name. Resources will be created with the name of your worker as the prefix"; details below are SRC `wrangler@4.166.0` `provisionBindings` / `D1Handler` / `KVHandler` / `R2Handler`, not exercised against the API). It is on by default for `wrangler deploy` (hidden flags `--experimental-provision` and `--experimental-auto-create`, both default `true`):
  - `d1_databases` entry **with** `database_id`: used as is; a wrong ID fails the upload. With `database_name` only: wrangler looks the database up by name and binds to it; if no database has that name it **creates** one.
  - `kv_namespaces` entry without `id`: reuses the binding of the same name on the already-deployed Worker, otherwise **creates** a namespace called `<worker-name>-<binding>`. There is no lookup by title, so it never finds the Pulumi-created namespace.
  - `r2_buckets`: `bucket_name` is the identifier. If the bucket does not exist (and the deployed Worker does not already have that binding), wrangler **creates** it with default settings.
  - `wrangler deploy --dry-run` accepts ID-less entries without any error or warning (RUN).
  Consequences for architecture C: keep explicit `database_id` and KV `id` in the config (the drift check then means something); always run `pulumi up` before the first `wrangler deploy`, because a deploy that runs first creates `bluelytics-media` itself and the later `R2Bucket` create then conflicts and has to be imported (`location` is "only honored the first time a bucket with a given name is created", SCHEMA); and note that the deploy token (R2 Write, KV Write, D1 Edit) is able to create these resources. `--experimental-provision=false` is accepted by 4.166.0 (RUN dry-run) and gates `provisionBindings` in the source, but it is a hidden experimental flag: UNVERIFIED as a supported way to turn this off.
- Wrangler refuses to run from a directory whose parent holds another project's `.wrangler/deploy/config.json` ("Found both a user configuration file ... and a deploy configuration file ... do not share the same base path"). Keep each Worker in its own package directory and run wrangler from there.
- IDs are not secrets and never change unless the resource is replaced. Commit them and guard with a check.

`scripts/check-wrangler-ids.mjs` (RUN: exit 0 on match, exit 1 with a message on mismatch)

```js
// Usage: pulumi stack output --json | node scripts/check-wrangler-ids.mjs apps/api/wrangler.jsonc apps/web/wrangler.jsonc
import fs from "node:fs";

const outputs = JSON.parse(fs.readFileSync(0, "utf8"));
const required = {
  d1DatabaseId: outputs.d1DatabaseId,
  kvNamespaceId: outputs.kvNamespaceId,
  r2BucketName: outputs.r2BucketName,
};
let failed = false;
for (const file of process.argv.slice(2)) {
  const text = fs.readFileSync(file, "utf8");
  for (const [key, value] of Object.entries(required)) {
    if (typeof value !== "string" || value.length === 0) {
      console.error(`stack output ${key} is missing`);
      failed = true;
    } else if (!text.includes(`"${value}"`)) {
      console.error(`${file}: does not reference ${key}=${value}`);
      failed = true;
    }
  }
}
process.exit(failed ? 1 : 0);
```

As written it requires every listed file to contain all three values; trim `required` per file if the web Worker only binds D1.

### 11.5 Cutover order (derived from sections 6.1 and 8.1)

1. `pulumi up` for storage only; import any existing entry point rulesets and DNS records rather than recreating them.
2. Deploy both Workers **without** `routes` (temporarily `workers_dev: true`, or a staging hostname such as a new subdomain as a custom domain) and load data.
3. Lowest-risk switch for the API: a plain route (`"pattern": "api.<zone>/*", "zone_name": "<zone>"`) on the existing proxied DNS record. Removing the route restores the old origin immediately. Requires the existing record to be proxied: check first.
4. Final state: `custom_domain: true` routes. The first CI deploy containing them replaces the existing DNS records for those hostnames without a prompt (6.1). Remove any Pulumi `DnsRecord` for those hostnames from state beforehand (`pulumi state delete`, not destroy).

```yaml
      - uses: actions/checkout@v7
      - uses: pnpm/action-setup@v6
      - uses: actions/setup-node@v7
        with:
          node-version: 24
          cache: pnpm
      - run: pnpm install --frozen-lockfile
      - run: pnpm --filter "./apps/*" build          # astro build must precede wrangler deploy

      - name: dry run (pull requests)
        if: github.event_name == 'pull_request'
        run: |
          (cd apps/api && pnpm exec wrangler deploy --dry-run)
          (cd apps/web && pnpm exec wrangler deploy --dry-run)

      - name: migrate D1
        if: github.event_name == 'push'
        working-directory: apps/api
        run: pnpm exec wrangler d1 migrations apply bluelytics --remote

      - name: deploy API
        if: github.event_name == 'push'
        working-directory: apps/api
        env:
          X_API_SECRET: ${{ secrets.X_API_SECRET }}
        run: |
          node -e 'process.stdout.write(JSON.stringify({ X_API_SECRET: process.env.X_API_SECRET }))' > "$RUNNER_TEMP/secrets.json"
          pnpm exec wrangler deploy --secrets-file "$RUNNER_TEMP/secrets.json"
          rm -f "$RUNNER_TEMP/secrets.json"

      - name: deploy web
        if: github.event_name == 'push'
        working-directory: apps/web
        run: pnpm exec wrangler deploy
```

Notes:

- `wrangler deploy --dry-run` needs no token (RUN with `CLOUDFLARE_API_TOKEN` unset).
- Migrations run before the code deploy, so each migration must stay compatible with the currently deployed code.
- If both workflows trigger on one push, infra must finish first when new IDs are introduced; in practice infra changes land in their own commit because the IDs have to be committed to `wrangler.jsonc` anyway.
